# ADR-0001: Brownfield 增量改造策略

- 状态: Accepted
- 日期: 2026-08-06
- 决策者: 项目团队

## 背景

系统存在一个初版，包含：
- 核心引擎 `core/`（7 个模块，逻辑完整）
- 后端 `backend/`（FastAPI，4 套并行业务路由）
- 前端 `frontend/`（只有构建产物，源码缺失）
- Streamlit 单文件原型 `app.py`

改造目标是企业级、可对外开放。面临选择：
1. **全盘重写**（greenfield）：从零开始，保留 core/
2. **增量改造**（brownfield）：在现有基础上规范化，保留能用的部分

## 决策

采用 **Brownfield 增量改造**（Path B），依据 addyosmani/agent-skills 的 adoption-guide。

理由：
- core/ 引擎逻辑完整，重写浪费且引入新 bug 风险
- auth/projects 路由基础具备，仅需加固
- 真正的问题是"散"（4 套路由、文件存储、无测试、无安全），不是"错"
- 增量改造每阶段可交付，风险可控

## 后果

**好处**：
- 保留核心资产，不重写引擎
- 每阶段交付可运行系统
- 渐进式质量提升

**代价**：
- 需先写特征化测试固化现有行为（阶段1工作量增加）
- 改老代码有风险（靠测试网兜底）
- 阶段3前端仍需重写（不可避免，源码缺失）

**不变量**：
- 改任何老代码前先写特征化测试
- core/ 公开接口不破坏性变更
