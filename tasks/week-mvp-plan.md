# 一周交付计划：外服账单系统 2.0 Web MVP

> 目标：在五个完整工作日内，将现有前端和后端收敛为可由财务人员完成一次月度薪资核算的 Web 系统。本文是 `plan.md` 的短期交付切片；其中未纳入的长期企业化能力继续按 `plan.md` 规划推进。

## 1. 已确认的目标与工作假设

### 已确认

- 交付形态为完整 Web 系统，而非仅后端 API。
- 采用 Brownfield 增量改造：保留 `core/` 的 Excel、实体、差异和校验能力。
- 业务主线收敛到 `/api/pipeline`，以 6 个阶段驱动一次核算。

### 已确认的执行前提

1. 一周指 5 个完整工作日，由一个研发人员执行；如按自然周连续投入，可将第 6～7 天用于 UAT 和修复。
2. 首版面向内部财务用户。最小权限为“已登录且所属租户”，本周不新增角色、审批流或企业 SSO。
3. 验收采用工作区中的真实业务 Excel；这些文件只在本地工作区和最终内网部署环境中处理，不上传、不外传，也不写入文档、日志或测试断言。
4. 历史数据必须迁移：当前发现 1 个 SQLite 数据库、7 个 session JSON、6 个上传文件和 1 个导出文件。迁移必须保留关联关系，并提供可复核的迁移报告。
5. 交付环境为公司内网 Docker 主机。开发环境允许 SQLite；演示/交付环境使用 PostgreSQL。

### 已完成的真实文件识别（仅结构信息）

- 已识别出一份多工作表、公式密集的工资 Master 模板；其“工资核算”工作表包含 98 列和两千余个公式，是导出时必须无损保留的基准。
- 已识别出包含考勤、奖金、人员异动、补发补扣等工作表的月度来源表。
- 已识别出含养老、失业、工伤、医疗、住房公积金等字段的社保公积金表。
- 遗留 SQLite 中有 2 个项目和 5 条上传文件记录，而磁盘上有 6 个上传文件。这意味着至少有 1 个文件尚未建立可靠的数据库关联；迁移前必须先做“文件—项目—类型”对账，不能按目录名称或文件名猜测归属。

## 2. 一周可交付范围

### 必须完成（Definition of Done）

财务用户能够：

1. 注册或登录，且只能访问本租户项目。
2. 创建指定薪资月份的项目；上传、查看、删除来源 Excel 和 Master 模板。
3. 按工作台指引完成：原始库加载 → 来源数据抽取 → 异动计算 → 异动确认/忽略 → 最终库构建/校验 → Excel 导出下载。
4. 在导出前看到阻断项与警告项；存在阻断项时不得导出。
5. 下载的 Excel 保留模板中的公式和格式；导出操作可追溯到项目和用户。
6. 将现有 SQLite、session JSON 和关联文件迁移至新存储；迁移前后按记录数、项目数和文件校验值复核。
7. 通过端到端冒烟测试，并能以 Docker Compose 启动。

### 明确不纳入本周

- 企业 SSO、细粒度 RBAC、多人审批流、消息通知。
- 历史 SQLite/JSON 数据迁移（除非确认必须）。
- 多 Master 模板的可视化配置器、对象存储、云端部署、复杂报表和移动端。
- 对 `core/schema_config.py` 的实体定义或 `EXPORT_MAPPING` 做业务变更。

## 3. 目标架构与依赖关系

```text
Next.js 14 Web（现有页面，收敛为 Pipeline 工作台）
      │ Bearer JWT + REST
FastAPI（auth / projects / pipeline）
      │
SQLAlchemy + Alembic ── PostgreSQL（交付）
      │
core/（归一化、实体、差异、校验、无损 Excel 导出）
      │
租户隔离的本地文件目录（上传模板、来源文件、导出文件）
```

### 关键约束

- 所有项目、文件和 pipeline 查询均经当前用户的 `tenant_id` 校验。
- 前端仅调用 `auth`、`projects`、`pipeline` 三组 API；旧 `modules`、`payroll`、`entities` 路由在新链路验收前仅作兼容，不继续扩展。
- 配置、数据库连接和 JWT 密钥通过环境变量注入；生产环境不得存在默认 JWT 密钥。
- Schema 变更通过 Alembic；不以 `create_all()` 作为生产建表路径。

## 4. 执行顺序（按垂直切片）

### Day 1：基线、真实样本受控盘点与迁移设计

- [ ] T1 建立可复现基线：锁定 Python/Node 版本、补齐运行依赖声明、验证现有前后端启动和测试。
  - 验收：新人按 README/开发文档可启动 API 与 Web；记录当前失败项，不掩盖失败测试。
  - 验证：`pytest`、`npm run lint`、`npm run build`。
  - 依赖：无；新增/锁定依赖须获批准。
- [ ] T2 盘点真实 Excel 与遗留数据，制定不可逆写入前的迁移清单与回滚方案。
  - 验收：为每个项目、session、上传和导出文件生成仅含 ID、类型、大小、哈希和记录数的清单；先修复现有“6 个磁盘上传文件 / 5 条数据库记录”的归属差异；原始数据只读备份，迁移工具可重复运行。
  - 验证：迁移前后记录数、项目数、文件 SHA-256 和可打开性一致；不得在终端输出姓名、证件号、工资金额等内容。
  - 依赖：业务方确认当前工作区数据可作为验收标准。

**检查点 A：** 团队确认迁移清单、备份位置和核对结果；未通过前不写入 PostgreSQL、不删除任何旧数据或旧路由。

### Day 2：安全与持久化基础

- [ ] T3 配置分层、生产密钥校验及 PostgreSQL/Alembic 初始化。
  - 验收：开发/生产环境的数据库 URL 与 JWT 密钥均不硬编码；空 PostgreSQL 可用 migration 建库。
  - 验证：`alembic upgrade head`、缺失生产密钥时启动失败的测试。
  - 依赖：T1；数据库 schema 改动需先批准。
- [ ] T4 按租户保存 pipeline 会话、上传文件元数据和导出审计记录，并执行可重复的遗留数据迁移。
  - 验收：重启 API 后项目工作进度仍可读取；跨租户项目、文件和导出访问返回 403/404；迁移后每一项遗留数据均可追溯到新记录或得到明确的异常原因。
  - 验证：FastAPI 集成测试覆盖重启后读取及跨租户拒绝；迁移报告的数量和文件哈希复核通过。
  - 依赖：T3。

### Day 3：后端月度核算闭环

- [ ] T5 固化 `core/` 与 pipeline 的特征测试，覆盖成功路径、缺列/缺值阻断和公式保留。
  - 验收：测试包含至少一套 UAT Excel；不修改 `core/` 公开配置。
  - 验证：`pytest --cov=core --cov=backend`；关键 engine 与 pipeline 路由测试通过。
  - 依赖：T2。
- [ ] T6 将项目上传、pipeline 六阶段、校验和导出 API 的响应契约统一，并只保留新前端所需字段。
  - 验收：可通过 Swagger 或 API 测试从项目创建一路执行至导出；错误均返回明确的用户可读信息。
  - 验证：`pytest backend/tests/routers/test_pipeline.py` 与导出下载测试。
  - 依赖：T4、T5。

**检查点 B：** 不打开前端页面，仅用 API 完成一次 UAT 样本的导出。此项失败时优先修后端，不进入前端重构。

### Day 4：前端工作台闭环

- [ ] T7 将现有登录、项目、sources、mapping、audit、export 页面接入统一 API，并移除对旧 `payroll/modules/entities` 客户端调用的依赖。
  - 验收：每一步展示输入状态、处理中状态、可恢复错误和下一步提示；阻断项清晰可见。
  - 验证：浏览器手工走通 UAT 样本；`npm run lint`、`npm run build`。
  - 依赖：T6。
- [ ] T8 增加前端路由守卫、会话失效处理和导出下载体验。
  - 验收：未登录不可访问工作台；401 自动回到登录；下载文件名可识别项目/月度。
  - 验证：前端单元测试或 Playwright 冒烟脚本。
  - 依赖：T7。

### Day 5：发布验证与验收

- [ ] T9 建立 Docker Compose、环境变量示例、健康检查和操作手册。
  - 验收：全新环境用一个命令启动 Web、API、PostgreSQL；不把真实 `.env`、密钥或样本薪资数据纳入版本库。
  - 验证：`docker compose up -d --build`，访问健康检查并执行一轮 UAT。
  - 依赖：T3、T8。
- [ ] T10 完成安全检查、回归测试、UAT 和交付清单。
  - 验收：所有自动测试、构建、关键安全检查通过；产品方确认一次完整核算导出。
  - 验证：完整测试命令、浏览器 E2E 冒烟、导出文件人工抽查。
  - 依赖：T9。

**检查点 C（交付门槛）：** 登录、租户隔离、项目创建、上传、六阶段 pipeline、阻断校验和 Excel 下载均通过；否则不宣称“完整 Web MVP”完成。

## 5. 风险、取舍与缓解

| 风险 | 影响 | 本周处理方式 |
|---|---|---|
| 样本模板与 `schema_config` 不匹配 | 导出错误，影响核心交付 | Day 1 先验证一套模板；不在临近交付时改核心映射 |
| PostgreSQL 与历史数据迁移扩大范围 | 挤占前端闭环时间 | Day 1 先做只读清单和回滚方案；Day 2 完成一次可复跑演练。迁移为已确认范围，不以 SQLite MVP 替代正式交付 |
| 旧路由存在重叠逻辑 | 前后端调用混乱 | 前端先切至 pipeline；回归通过后再删除旧路由，删除须单独确认 |
| 薪资数据敏感 | 合规与泄露风险 | 脱敏样本、环境变量密钥、按 tenant 存储、禁止将上传/导出目录纳入 Git |
| 范围扩张 | 一周无法验收 | 新需求进入下周候选池，先保证一个模板的一次完整闭环 |

## 6. 每日同步格式

每天结束前记录：完成的任务与验证证据、阻塞项、次日计划、是否影响交付日期。任何 schema、依赖、核心公开接口或文件删除的变更，先得到批准再执行。

## 7. 已确认的验收基准

- 采用工作区现有的真实工资 Master、月度来源和社保公积金 Excel 进行本地 UAT。
- 首版只提供内部财务用户的登录与租户隔离；角色、审批与 SSO 不进入本周范围。
- 全量迁移既有 SQLite、session JSON、上传和导出数据；不能因迁移复杂而降级为“只演示、不迁移”。
